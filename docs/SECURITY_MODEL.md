# InvoiceShield v0.2 — модель безопасности (учебная)

## Защищаемые активы

- Банковские реквизиты и имена поставщиков.
- Данные счетов и результаты антифрод-анализа.
- Аудит действий сотрудников.
- Пароли и действительные сессии.

## Границы доверия

**Браузер → FastAPI:** все входящие данные потенциально недоверенные. Проверяем сессию, права пользователя и CSRF на каждом изменяющем запросе; Pydantic валидирует тело API.

**FastAPI → SQLAlchemy → БД:** параметризованные ORM-запросы, атомарные транзакции анализа; строгая проверка полномочий перед записью.

**Локальный администратор → CLI:** создание пользователей из терминала — привилегированная операция с доступом к файлам приложения, отдельного веб-эндпоинта создания администраторов нет.

## Контрольные меры

1. **Пароли:** Argon2id через `argon2-cffi` с индивидуальными солью и параметрами work factor. В БД находится хеш, не исходный пароль.
2. **Сессии:** сервер создаёт криптографически случайный 256-битный токен, хранит только SHA-256 токена (`AuthSession.token_hash`) и проверяет истечение через 8 часов. На logout сессия удаляется из БД, старый токен больше не работает.
3. **Cookie:** `HttpOnly`, `SameSite=Strict`, `Path=/`, `Max-Age=28800`. В локальном HTTP-режиме `Secure=False`; на HTTPS установить `COOKIE_SECURE=true` и использовать `__Host-` имя cookie.
4. **CSRF:** synchronizer token хранится на сервере в строке сессии и отправляется в скрытом HTML поле или заголовке `X-CSRF-Token`. Отдельно защищён вход через double-submit token cookie/поле.
5. **RBAC:** права проверяются **на сервере** (API и веб-обработчики). Скрытие кнопки в UI не считается проверкой доступа.
6. **CSP:** JavaScript вынесен во внешний файл, CSP запрещает inline-скрипты и чужие источники. Шаблоны Jinja2 экранируют пользовательский ввод.
7. **Логи:** `security_events` связывают основные действия с ID пользователя и не пишут пароли, токены или полный номер счёта в `detail`.

## Ограничения и backlog

- **Не защищать реальные данные этой версией:** нет HTTPS в локальном режиме; нет MFA и ограничения частоты перебора паролей, нет восстановления пароля и ротации сессий; нет отзыва всех сессий пользователя.
- UI показывает банковские реквизиты в HTML `<option>` для удобства заполнения. Для реального бизнеса это требует отдельной политики маскирования и прав доступа.
- Копирование или восстановление БД должно осуществляться с контролем доступа; SQLite файл в незашифрованном виде.
- CSP и CSRF снижают риски, но не заменяют аудит зависимостей, pentest, TLS и контроль инфраструктуры.
- Входные данные PDF ещё не обрабатываются; импорт потребует специальной песочницы, ограничений на тип/размер и защиты от malware и ZIP bombs.
- Текущий `create_all` сохраняет старые таблицы, но **не выполняет ALTER TABLE**. До изменения существующих колонок нужна отдельная миграционная система (Alembic).

Основа для требований: OWASP Session Management Cheat Sheet и OWASP CSRF Prevention Cheat Sheet.
