# Урок 2. Что происходит, когда пользователь входит в InvoiceShield

## 1. Пользователь создаётся локально

Команда:

```bash
python -m scripts.manage_users add --username analyst --role analyst
```

`getpass.getpass()` вводит пароль без отображения в терминале. `app/auth.py::create_user()` проверяет формат логина, длину пароля, роль и вызывает `PASSWORD_HASHER.hash(password)`. Соль входит внутрь полученного Argon2id-хеша.

**Задание:** найди в `app/models.py` таблицу `User` и ответь, почему в ней нет колонки с исходным паролем.

## 2. Запрос на вход

Браузер отправляет POST `/login` с логином, паролем и CSRF-токеном. `routes_auth.py` проверяет CSRF, ищет пользователя, сверяет введённый пароль с хешем через `check_password()` и вызывает `new_session()`.

`new_session()` создаёт случайный токен через `secrets.token_urlsafe(32)`. Браузер получает его в `HttpOnly` cookie, а база — **SHA-256 хеш** токена. Этот токен работает до истечения сессии или выхода пользователя.

**Задание:** открой `app/auth.py`; найди `hash_token()` и `set_session_cookie()`.

## 3. Авторизация запроса

Для GET `/api/invoices` сервер вызывает `require_api_user()`. Внутри `lookup_identity()` получает cookie, хеширует токен, ищет его в таблице `auth_sessions`, проверяет срок и активность аккаунта.

Без действительной сессии API отвечает `401 Unauthorized`. Поэтому пользователь, просто знающий URL API, не получает доступ к счетам.

## 4. Зачем нужна CSRF-защита

Cookie браузер отправляет автоматически. Поэтому злоумышленник может попытаться заставить браузер авторизованного пользователя выполнить нежелательный POST-запрос. В InvoiceShield у каждого сеанса есть дополнительный секретный CSRF-токен. Для HTML он передаётся в скрытом поле, для API — в заголовке `X-CSRF-Token`.

**Задание:** в `app/routes_web.py` найди вызов `verify_csrf()`. Затем запусти `test_csrf_blocks_html_and_api_writes` из `tests/test_auth.py` и посмотри, почему ожидается HTTP 403.

## 5. RBAC: роль не равна интерфейсу

`analyst` видит таблицу поставщиков, но не может создавать новых. При попытке POST `/api/suppliers` с действительной сессией проверка `ensure_admin()` возвращает 403.

**Важно:** даже если скрыть кнопку на странице, атакующий может вызвать API напрямую. Поэтому проверка должна происходить на сервере.

## 6. Практика

1. Создай аккаунт `analyst` и зайди под ним. Убедись, что добавление поставщиков недоступно.
2. Проверь счёт — эта операция должна работать.
3. Выйди и попробуй открыть `/api/invoices`: получишь 401.
4. Выполни `python -m pytest -v tests/test_auth.py`, изучи 9 security-тестов.

## Термины для собеседования

- **Authentication:** кто ты? Проверка логина/пароля.
- **Authorization:** что тебе разрешено? Проверка роли и доступа.
- **Session:** временное состояние входа пользователя.
- **CSRF:** подделка действий в браузере от имени авторизованного пользователя.
- **Argon2id:** алгоритм для безопасного хранения паролей в виде ресурсоёмких хешей.
- **RBAC:** Role-Based Access Control — модель разграничения доступа по ролям.
