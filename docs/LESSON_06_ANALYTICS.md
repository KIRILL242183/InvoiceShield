# Урок 6. Как строится отчёт о рисках на Python

## Путь запроса

`GET /analytics` → `app/routes_reports.py` (валидация фильтров и проверка сессии) → `app/services/analytics.py` (чтение счетов) → Jinja2 `app/templates/analytics.html` (отображение).

## Что такое агрегирование?

Счета имеют атрибуты `amount_kopecks`, `risk_level` и `supplier_id`. Агрегирование суммирует числовые значения и считает, сколько счетов попало в каждую категорию. Суммы хранятся **в целых копейках**, а в рубли переводятся при выводе через `Decimal` — это исключает ошибки округления `float`.

Отдельно считаем инциденты `OPEN`, `IN_REVIEW`, `RESOLVED` и `FALSE_POSITIVE`. За основу берутся счета, отфильтрованные по дате их **выставления**. Из одного счёта нельзя делать вывод о фактической оплате или предотвращённом убытке.

## Почему ограничение 5000 записей?

Первая версия использует ограниченную выборку и расчёт в Python. При большем количестве строк API возвращает HTTP 413 и просит уточнить фильтры. Производственный сервис должен считать основные агрегаты через SQL `GROUP BY`, использовать постраничную обработку и фоновые задания для экспорта больших объёмов.

## Почему CSV — отдельный endpoint?

`GET /api/analytics/export.csv` проверяет сессию и роль `admin` на сервере. Файл не содержит номера банковского счёта; строки из документов экранируются, если могут интерпретироваться Excel/LibreOffice как формулы. HTML-скрытие кнопки у аналитика — дополнительное удобство, а **не** механизм защиты.

## Мини-задание

1. Создай три вымышленных счёта с LOW, MEDIUM и HIGH риском.
2. Открой `/analytics` и сравни счётчики и сумму счетов.
3. Выстави фильтр `risk_level=HIGH` и сравни данные с `GET /api/analytics/summary?risk_level=HIGH` в Swagger.
4. Войди под `analyst` и проверь, что CSV-экспорт возвращает HTTP 403.

## Ограничения

Не предназначено для публичного размещения или реальных платёжных данных. Отчёт не заменяет финансовую отчётность; фильтры по `issued_on`, а не дате платежа.
