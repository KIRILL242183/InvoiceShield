# Урок 3. Как InvoiceShield расследует инциденты

Цель: научиться читать Python-код не по файлам в случайном порядке, а через путь одного бизнес-события.

## Пользовательский сценарий

1. Аналитик создаёт счёт, у которого банковские реквизиты не совпадают с зарегистрированными.
2. `POST /web/invoices` вызывает `register_invoice` из `app/services/invoices.py`.
3. `risk.evaluate()` рассчитывает `HIGH` и 70 баллов.
4. **В одной транзакции** сохраняются `Invoice`, `Incident`, `IncidentEvent` и запись общего аудита. После `commit()` данные становятся видны другим пользователям.
5. Страница `/incidents` показывает новый кейс со статусом `OPEN`.
6. Аналитик переводит его в `IN_REVIEW` и оставляет комментарий.
7. Администратор при необходимости назначает исполнителя, а после проверки аналитик переводит кейс в `RESOLVED` или `FALSE_POSITIVE`.

## Почему отдельная таблица `incidents`?

`Invoice` содержит финансовые данные и результат проверки, а `Incident` — процесс расследования. Один счёт может иметь рисковые сигналы, но статус расследования меняется отдельно от оценки риска. Связь `incident.invoice_id` уникальна: один кейс на один подозрительный счёт.

`IncidentEvent` — журнал действий по одному инциденту. Через API добавляются события; редактировать или удалять события нельзя. Это **не** криптографически защищённый журнал и не защита от администратора базы данных.

## Важный фрагмент: optimistic concurrency

```python
stmt = (
    update(Incident)
    .where(Incident.id == incident_id, Incident.version == expected_version)
    .values(version=Incident.version + 1, updated_at=_now(), **changes)
)
if db.execute(stmt).rowcount != 1:
    db.rollback()
    raise IncidentConflict
```

Представим две вкладки, которые загрузили инцидент версии 1. Первая изменила статус и увеличила версию до 2. Вторая пытается отправить старую форму с версией 1. Условие `WHERE version=1` не находит строку — сервер возвращает HTTP `409 Conflict`, а не незаметно перезаписывает данные.

Это **не** заменяет всех блокировок и бизнес-правил, но предотвращает простой сценарий потери изменений в кейсе.

## Почему нельзя доверять скрытой кнопке?

В HTML у аналитика нет формы назначения исполнителя. Однако HTTP-запрос можно сформировать вручную. Поэтому серверная функция `/api/incidents/{id}/assign` вызывает `ensure_admin(identity)`; аналогичная проверка есть и в веб-маршруте. Тесты подтверждают HTTP 403 для аналитика.

## CSRF и XSS

Формы отправляют CSRF-токен, привязанный к сессии. Даже если злоумышленник заставит браузер отправить POST-запрос с другого сайта, без токена запрос отклоняется. Jinja2 автоматически экранирует комментарии вроде `<script>`: текст показывается буквально, а не выполняется как код. Тест `test_comment_xss_escaped_and_size_checked` это проверяет.
